# 每次开发任务流程

本文件是流程导航，不复制各主题细则。先判断任务类型和当前阶段，只读取即将执行阶段的规范；阶段内内容未变时不重复读取。发布可跨多个开发任务，不要求每次 develop 提交都发布。

| 阶段 | 预想操作与按需阅读 | 完成证据 / 下一步条件 |
| --- | --- | --- |
| 1. 确认任务 | 读取 AGENTS.md 和本文件；核对目标仓库、分支、工作区和需求；只说明本次涉及的阶段 | 简短范围、验证计划、已有改动；纯模拟任务只描述预期，不执行操作 |
| 2. 本地开发 | 读取[本地开发](LOCAL_DEVELOPMENT.md)；代码改动再读[编码](CODING_STANDARDS.md)，涉及模块结构再读[架构](ARCHITECTURE.md)；规范文档任务只读需要修改的主题 | 最小改动、更新相关说明；项目介绍可替换，原版权和许可证不得冒领或删除 |
| 3. 检查与验收 | 读取[测试](TESTING_STANDARDS.md)，按本地开发矩阵执行格式、静态检查、相关测试和 Debug 打包；仅文档不编译，仅工作流做脚本/触发条件检查 | 记录命令、退出结果、包路径；设备不可用时明确未运行验收；阻塞按规范处理 |
| 4. 本地提交与上传 | 读取[仓库管理](REPOSITORY_WORKFLOW.md)，复核暂存区、远程目标和授权；验证通过的完整任务及时提交并普通推送 develop | 本地与远端完整 SHA 一致，不夹带其他任务文件 |
| 5. develop CI | 跟踪同一 SHA 的 EhReader CI，自动检查与 Debug 打包，下载入口交用户验收 | CI 终态和附件链接；失败修复后回到检查阶段；不生成 Tag/Release |
| 6. 发行准备与确认 | 需要发行时才读[发布规范](RELEASE_POLICY.md)；在 develop 准备未用版本和严格递增 versionCode，完成 CI，提出具体 PR/提交、版本和合并方案 | 用户确认后才能合并 develop → master；新增变更超出批准范围须重新核对 |
| 7. 正式发行 | 合并事件固定实际 merge SHA，CI 检查、正式签名、包校验，然后按版本创建 Tag、完整上传草稿并公开 Release | Tag、Release、构建与附件链接；缺凭据/冲突/失败停止，不绕过；重试遵循发布规范 |
| 8. 简短汇报 | 每次开发或更改结束都执行，无论是否进入发布阶段；简述本次内容、修改文件和结果 | 使用下方三项格式；有未完成事项时补一句原因，不重复过程日志 |

## 最后一步：简短汇报

默认用三项说明，尽可能简单清晰：

- **内容**：一句话说明本次开发或更改了什么。
- **文件**：列出实际修改的文件；文件较多时按目录分组，并提供完整差异链接。
- **结果**：明确成功、部分完成或失败，简述实际检查结果；未完成或未验证的事项及原因用一句话说明。

有提交、CI 或可下载产物时，按需补充简短 SHA 和相关链接；没有则省略。不复述执行过程，不堆砌日志，不把推送成功、跳过检查或未运行测试写成全部验证成功。

## 常用请求结尾

> 请先读 EhReader/AGENTS.md 和开发任务流程，确认本次阶段，再按阶段读取对应规范并执行。

文档维护说明见[规范说明](STANDARDS_README.md)，仅维护规范时需要阅读。工作流、签名、版本改动在动手前就应读取发布规范，因为它们直接影响发布边界。

打包范围：本地默认仅 arm64-v8a；GitHub Actions 按完整支持架构及 universal 生成，细则见本地开发规范。
