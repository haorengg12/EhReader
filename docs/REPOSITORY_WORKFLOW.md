# 仓库管理规范 — V2.1

本文件是分支、授权、提交、推送、CI 跟踪及合并的权威来源。各阶段顺序见[开发任务流程](DEVELOPMENT_FLOW.md)，正式发行细则见[发布规范](RELEASE_POLICY.md)。

## 状态与授权范围

用户于 2026-11-03 确认默认分支 master、开发分支 develop 和 develop 验证后由用户确认合入 master 的流程。本规则替代 V2.0 审阅稿中的未启用说明。

在用户已授权的 EhReader 开发任务内，本地必要验证通过后，AI 可对本次任务文件提交，并普通快进推送到 haorengg12/EhReader 的 develop，无须逐次询问。推送后跟踪 CI，失败可修复本任务并重新验证、推送；临时故障可重跑同一开发验证任务。发现远端竞争先检查差异，不强推覆盖。

常规授权不包含：创建或修改 PR、创建其他远端分支、修改仓库设置、强推、删除分支或标签、移动标签、写入旧仓库。需要时先准备可审查内容再取得明确授权；已批准的同一操作不重复请求。本次分支重命名和默认分支修改已有用户明确授权，不推广为未来任意设置修改权限。

master 合并始终需要用户确认具体 develop 提交/PR、合并方式及预期版本。确认同时授权实际合并结果的自动 Tag/Release 流水线；无需再次逐项确认 Tag。新增变更超出批准范围时重新核对。禁止 AI 自行认定 CI 通过等于批准合并。

## 分支与任务交付

- master：远端默认分支，只接收用户批准的发行合并；默认分支不等于日常开发分支。
- develop：日常集成和自动 Debug 打包。现有克隆应同步远程并显式检出 develop，不能在默认 master 上直接开发。
- 提交前复核暂存区，不夹带其他任务文件。每个验证通过的完整任务单元及时推送，不逐文件推送，也不长期积压。
- 普通开发不自动修改版本号；正式发行前在 develop 准备版本并验证，版本来源与算法见发布规范。
- develop push 自动触发 EhReader CI；PR 目标 develop/master 执行验证；develop 不生成 Tag 或 Release。

## CI 与用户确认

1. 推送前后记录完整 SHA，确认 origin/develop 接受的提交。
2. 按仓库、工作流、事件和 SHA 定位 CI，监控成功、失败或取消；超时、服务不可用或工具无法继续时报告真实状态和链接，不承诺未建立的后台监控。
3. 失败检查日志，区分本任务问题和环境/历史问题；不关闭检查掩盖失败，不将跳过、取消、NO-SOURCE 当作通过。
4. CI 成功后提供运行及附件链接，供用户验收；不能只报告“推送成功”。
5. 提请合并时提供 develop SHA、差异摘要、CI 和验收结果、versionName/versionCode、预期 Tag，并明确合并会自动启动正式发行。
6. 仅通过本仓库 develop → master 的 PR 合并进入自动发布。用户确认后执行指定合并；直接 push master、其他来源 PR、未合并关闭 PR、手动 Tag 都不会触发新发布流程。
   master 应将 `build` 和 `Release readiness` 配置为 GitHub Actions 必需检查，要求分支与 master 同步，并对管理员同样生效；零必需审批人数允许仓库所有者自行合并已获确认且检查通过的 PR。保护开启时不得绕过红灯合并；需要同步 master 时先更新 develop 再等待新检查。具体启用状态需通过 GitHub API 核实。
7. 固定实际 merge SHA 重新构建正式包，不把 develop Debug 包当正式包；继续监控发行结果并报告附件和阻碍。

## 技术启用状态

工作流变更先在 develop 验证，须经用户批准合入 master 才部署正式发布逻辑。首次迁移应一并替换 master 上的上游标签工作流、旧应用身份和签名引用；迁移完成前不得操作旧 master 的标签发布逻辑。

正式 CI 需配置签名 Secrets；缺失时发布失败，不回退。分支/标签保护属于独立远端配置，未经核实不得宣称已经启用；合并前应核对保护、签名、版本和所需检查。规范不能代替服务端访问控制。
