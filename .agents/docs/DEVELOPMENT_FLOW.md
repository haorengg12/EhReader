# 每次开发任务流程

本文件是流程导航，不复制各主题细则。先判断任务类型和当前阶段，只读取即将执行阶段的规范；阶段内内容未变时不重复读取。发布可跨多个开发任务，不要求每次 develop 提交都发布。

本文件位于工作区 `D:\Eh项目改造\EhReader\.agents\docs`，EhReader Git 仓库位于 `D:\Eh项目改造\EhReader`。入口分别是[工作区 AGENTS.md](../../../AGENTS.md)和[仓库 AGENTS.md](../../AGENTS.md)；目录用途统一见[本地开发规范](LOCAL_DEVELOPMENT.md#工作区目录约定)。

| 阶段 | 预想操作与按需阅读 | 完成证据 / 下一步条件 |
| --- | --- | --- |
| 1. 确认任务 | 读取 AGENTS.md 和本文件；核对目标仓库、分支、工作区和需求；只说明本次涉及的阶段 | 简短范围、验证计划、已有改动；纯模拟任务只描述预期，不执行操作 |
| 2. 本地开发与版本准备 | 读取[本地开发](LOCAL_DEVELOPMENT.md)；代码改动再读[编码](CODING_STANDARDS.md)，涉及模块结构再读[架构](ARCHITECTURE.md)；应用下方版本默认策略，需要新版本时读[发布规范](RELEASE_POLICY.md)并确认目标；规范文档任务只读需要修改的主题 | 普通改动默认不升版，不等待形式确认；新测试包交付或发行前明确版本，版本修改与开发一起完成 |
| 3. 自动检查与产物验证 | 读取[测试](TESTING_STANDARDS.md)，按本地开发矩阵执行检查；本地打包通过 Docker，仅生成 ARM64 Debug，执行[Docker 检查与验收](LOCAL_DEVELOPMENT.md#docker-检查与验收)中的构建检查，临时替换仅应用于容器源码副本；仅文档不编译 | 核对工具链/缓存隔离、替换清单与有效性、原仓库完整性、APK 身份与架构；导出日志和校验清单；人工测试安排进入下一阶段 |
| 4. 最终审核 | 用同一份最终审核单列明结果、版本、范围、测试安排与提交推送权限；复用已有明确答复，只一次性询问真正缺少的决定；不要求上传的代码任务按已有授权做本地提交 | 必要检查通过后可按本地提交约定进入第 5 阶段保存；推送仍复核测试安排和权限 |
| 5. 本地提交与上传 | 读取[仓库管理](REPOSITORY_WORKFLOW.md)，复核暂存区、固定比较基准、版本路径和授权；必要检查通过后按本地提交约定 git commit 到 develop；仅在上传条件满足时推送目标分支 | 本地提交记录 SHA；获准推送后核对本地与远端完整 SHA 一致，不夹带其他任务文件；“无需等待”不等于“人工测试通过” |
| 6. 按版本路径处理 | 跟踪同 SHA 基础验证；按[分流](RELEASE_POLICY.md#基础验证与打包分离p1-13)处理第三位 Debug/Tag、第一二位发行准备或仅保存 | 分别记录基础验证、打包及发行状态；第三位附产物和开发 Tag，不自动进入 master |
| 7. 发行准备与确认 | 仅第一、二位升版进入；读取[发布规范](RELEASE_POLICY.md)，复核未用版本、递增 versionCode、本地检查及只读预检，准备具体 PR/提交和合并方案；需补改版本时回第 2 阶段，重新检查和验收后分流 | 不要求重复 develop/PR 构建；用户确认且实际保护满足后才能合并 develop → master；新增变更超出批准范围须重新核对 |
| 8. 正式发行 | 合并事件固定实际 merge SHA，CI 检查、正式签名、包校验，然后按版本创建 Tag、完整上传草稿并公开 Release | Tag、Release、构建与附件链接；缺凭据/冲突/失败停止，不绕过；重试遵循发布规范 |
| 9. 核对记录与交付 | 核对提交前已写的 [ACCEPTANCE.md](ACCEPTANCE.md) 和最终证据；仅本地任务在交付前追加，提交后的结果用 CI summary 或 temp 外部证据保存 | 保留历史，不为追写本次 SHA/CI 自动新增提交；缺项如实记录 |

本地提交和上传分开执行：用户于 2026-11-10 已持续授权每次代码修改通过必要检查后，在 develop 做一次本地提交，不创建 Tag、不自动推送；细则见[本地代码提交约定](REPOSITORY_WORKFLOW.md#本地代码提交约定2026-11-10)。该本地保存路径不等待设备验收，除非用户明确要求等待；如实记录未测项。下文将 commit 与 push 共用等待条件的表述仅适用于上传流程。

## 节点推荐组合

以下是本项目的模型与推理等级建议。默认使用 **GPT-6.1 Sol + High**，减少阶段间切换；表中 Medium 是相应节点可选的节省资源配置，不要求每进入一个节点就切换。

| 开发流程节点 | 推荐模型 | 推理等级 | 使用说明 |
| --- | --- | --- | --- |
| 1. 确认任务 | GPT-6.1 Sol | High | 理解需求、范围、已有改动和验收条件；大型架构迁移可选 Astra + XHigh |
| 2. 本地开发与版本准备 | GPT-6.1 Sol | High | 常规实现、应用版本默认策略并完成所需修改；复杂并发、数据库迁移、核心架构调整可选 Astra + XHigh |
| 3. 自动检查与产物验证 | GPT-6.1 Sol | Medium | 执行检查、核对日志和产物；疑难失败先升 High，仍难定位再考虑 Astra + XHigh |
| 4. 最终审核 | GPT-6.1 Sol | Medium | 针对最终材料用同一审核单处理测试安排与保存权限，只补齐缺项 |
| 5. 本地提交与上传 | GPT-6.1 Sol | Medium | 核对差异、暂存区、授权和目标分支，执行提交推送 |
| 6. 按版本路径处理 | GPT-6.1 Sol | Medium | 跟踪第三位版本的 CI、产物和开发 Tag，或按规则跳过；需要修复时按第 2 节点重新选择 |
| 7. 发行准备与确认 | GPT-6.1 Sol | High | 综合检查具体提交、版本、CI、发布条件和合并方案 |
| 8. 正式发行 | GPT-6.1 Sol | Medium | 执行已批准操作，核对签名、Tag、Release 和附件；异常涉及发布逻辑时升 High |
| 9. 核对记录与交付 | GPT-6.1 Sol | Medium | 根据实际证据核对任务记录与收尾材料 |

- 表中 Astra 指 GPT-6 Astra。Max、Ultra 不绑定固定节点：第 1、2 节点需要深入推理的单个难题可考虑 Max；第 1、2、3 节点涉及可独立拆分的大型分析或审查时可考虑 Ultra。
- 需要升级时简短说明当前节点、具体难点及推荐组合，由用户决定是否切换；建议本身不新增等待条件，用户明确要求等待切换时暂停相关工作。
- 无法可靠确认当前模型或推理等级时不推测，不声称已完成切换；实际选项以客户端为准。模型选择不改变各阶段的验证、授权及发布条件。
- 本表为项目使用建议，参考 [OpenAI 模型与推理等级说明](https://learn.chatgpt.com/docs/models)，不是官方固定配置或自动切换机制。

## 临时文件存放

所有阶段主动生成或导出的临时日志、排查记录、调试输出、临时报告和一次性辅助文件，统一存放在工作区根目录 `D:\Eh项目改造\temp`，不是 `EhReader/temp`。需要时创建目录，建议按 `temp/<日期-任务>/<阶段>/` 分组，避免文件混杂或覆盖其他任务记录；不将这些临时文件提交到仓库。

工具固定生成的容器中间文件和缓存按既有构建机制管理，需要导出用于排查时放入上述 temp 目录。用于本地构建的替换文件仍放在工作区 `build-tools/build-use-file`；本地 arm64-v8a APK 及配套校验清单、来源清单和最终验收报告放在工作区 `release`；最终简短结论追加到仓库[ACCEPTANCE.md](ACCEPTANCE.md)，必要时链接 temp 中的详细排查记录。废弃文件或目录回收到工作区 `trash`，不混入有效交付材料；目录管理遵循[工作区目录约定](LOCAL_DEVELOPMENT.md#工作区目录约定)。

本规则适用于后续文件存放，不自动迁移或删除既有记录。仅更新规范不代表现有构建脚本的日志输出路径已经适配。

## 版本准备（第 2 阶段）

人工测试之前先完成版本准备。2026-11-07 起采用以下默认策略；已有适用的明确版本指示直接沿用，不重复询问：

| 任务意图 | 版本处理与等待边界 |
| --- | --- |
| 普通功能修改、修复、文档或配置维护，未要求交付测试包或发行 | 默认保留 versionName/versionCode，简短说明“不升版”并继续本地工作，不发起版本问答 |
| 按验证矩阵执行必要编译、测试或 Debug 构建 | 必要检查本身不代表新版本或测试包交付意图，默认不升版；不因此减少检查 |
| 用户只说“打个测试包”等交付要求，未明确版本 | 先确认本次沿用现有版本还是升版，以及升版时的目标 versionName/versionCode，再生成最终交付包；可建议版本，不能自行决定 |
| 已明确“按当前版本打包”或给出目标版本 | 沿用该意图，核对合法性；已确认的信息不重复问 |
| 要求升版、发行，或变更版本分流但目标信息不全 | 只暂停依赖版本决定的修改、最终打包或发行准备，可继续不依赖该决定的本地实现；不得猜测版本或用旧包冒充最终材料 |

需要更新时读取[发布规范](RELEASE_POLICY.md)，确定版本路径后修改 `app/build.gradle.kts` 并核对引用。第四位用于测试版，明确源 SHA、四段版本及递增的安装编号，继续使用 develop。将最终源码、版本与说明交第 3 阶段检查，准备对应测试包或文档差异；第四位测试版按明确要求生成本地 ARM64 Debug，不创建 Tag/Release。

默认不升版只决定版本配置，不授权提交、推送或 master 合并，也不改变现有 CI/CD 的目标分流。上述准备完成后进入最终审核。

第 3 阶段可使用[本地任务调度入口](LOCAL_DEVELOPMENT.md#本地任务调度入口)按明确文件范围选择已有检查、Debug 构建及材料整理，生成 temp 下的任务状态和证据。继续任务时按[复用与失效规则](TESTING_STANDARDS.md#检查结果的复用与失效)核对每项输入及原证据，只重跑受影响检查，不能仅凭上次阶段或 SHA 沿用旧结果。该入口在提交推送前停下，不能自行取得第 4 阶段的人工测试或保存权限；缺项如实交审核单处理。

## 人工测试安排确认

第 4 阶段使用一份最终审核单，同时表达人工测试安排和提交推送权限，两者仍是独立条件。先自动完成本地实现、必要检查和可审阅材料，复用已有明确指示，再一次性列出缺少的决定；不固定拆成“要不要测试”和“能不能推送”两轮。

### 最终审核单

审核单默认使用下面六项，按任务规模简写；材料必须对应最终源码和实际版本：

- **改动**：本次结果及必要风险说明。
- **范围**：拟提交文件与最终差异链接，明确排除其他任务改动；尚无提交时不得虚构 SHA。
- **版本与目标**：不升版或具体 versionName/versionCode、适用分流及目标分支。默认保存目标为 develop；第四位测试版须列明源 SHA、versionCode 和 develop 分支。
- **验证**：本地检查真实结果、未运行项，以及人工测试状态：待安排、待结果、未通过、明确通过或明确无需等待。
- **材料**：对应包或文档差异、测试重点及必要证据链接；纯文档不为审核额外构建 APK。
- **处置**：本地交付或拟提交推送；逐项注明测试安排和推送权限哪些已有答复、哪些待决定，只询问缺项。

未要求提交推送、也没有适用保存授权的任务，默认交付本地结果，注明“尚未提交或上传”；不强制发起上传问答。代码任务已获本地提交授权时，完成本地 commit 后交付；“只保留本地”不等于禁止已授权的本地 commit。纯文档且无提交授权时直接交付。后续要求上传时，沿用同一审核材料并核对是否仍为最终状态，只补齐缺少的测试安排或授权。

需要保存到远端且仍缺少决定时，在同一审核单中列出可直接回复的处置方式：

| 用户明确答复 | 测试状态 | 提交推送权限及下一步 |
| --- | --- | --- |
| “先人工测试” | 等待本次材料的明确结果 | 未另行授权时不提交、不推送；测试失败回到本地修复 |
| “测试通过，允许提交并推送 develop” | 本次材料明确通过 | 同时取得本次范围的提交推送权限，复核后进入第 5 阶段，不再追问 |
| “无需等待人工测试，允许提交并推送 develop” | 明确无需等待，不记为测试通过 | 同时取得本次范围的提交推送权限，复核后进入第 5 阶段 |
| “只保留本地” | 如实记录已执行或未执行的测试 | 交付本地结果，不再问推送 |

表中 develop 同样适用于第四位测试版，审核单列明具体源 SHA、版本和安装编号。答复的权限含义、条件授权复用与失效以[仓库管理](REPOSITORY_WORKFLOW.md#状态与授权范围)为准：先核对已有明确指示，只问缺项，不增设形式审核。

需要等待测试或授权时，仅暂停受该条件限制的提交推送，不妨碍已授权且不依赖该答复的本地工作。超时、构建成功或 CI 成功均不能替代用户答复。

### 推送授权

本地代码提交按上述持续授权在必要检查通过后执行。推送前另外核对人工测试条件已满足、权限覆盖本次内容及目标；未满足时不 push。第 4 阶段不执行 commit，第 2 阶段的版本修改随第 5 阶段任务内容一起提交。

不在审核后常规升版；源码、目标版本、目标分支或范围发生实质变化时，回到相应本地准备与检查，更新同一审核单，重新取得受影响的验收或授权，不能沿用旧包测试通过结论。无关的已有明确决定不重复询问。检查有效性与 master 具体合并权限仍分别遵守测试、仓库及发布规范。

### 关键人工审核节点

1. **开始与实现阶段的例外决定**：目标实质不明、上述测试包/版本信息缺失、范围扩大、破坏性操作或新增权限时及时提问；范围明确的本地工作继续，不要求用户逐步批准。
2. **本次结果与保存**：需要上传且决定缺失时，用最终审核单一次询问；需要人工测试就等待明确结果，仅本地则交付结束，已有充分指示则直接复用。
3. **仅正式发行的具体确认**：第 7 阶段提供具体 develop SHA/PR、版本、合并方式和只读预检，单独取得具体 PR 操作与 master 合并授权；普通保存许可不覆盖发行合并。获准且实际保护满足后，连续执行相应操作及合并后的发行，不逐项再问 Tag/Release。

## 第 5～8 阶段连续推进

第 4 阶段放行后，连续执行第 5 阶段提交推送及第 6 阶段实际基础验证，再按[发布规范](RELEASE_POLICY.md#基础验证与打包分离p1-13)处理打包、开发 Tag 或发行准备；没有应运行的打包就不等待 APK。失败后返回受影响的准备、检查及审核，不因连续执行绕过权限。

第一或第二位进入第 7 阶段准备具体 SHA/PR、版本、本地结果、只读预检及合并方案；满足[具体合并权限](REPOSITORY_WORKFLOW.md#状态与授权范围)和实际保护后，连续执行获准操作与第 8 阶段。打包与发布条件见[发布规范](RELEASE_POLICY.md)，不将普通保存授权扩展为发行权限。

仅第三位升版、第四位测试版及不升版均跳过第 7、8 阶段并追加记录；以后需要发行须另行确认第一或第二位升版。缺少答复、授权、必要检查或发布条件时停在对应条件，不以“连续推进”绕过门禁。

## 失败恢复与重新审核

先保存实际命令、退出码/取消信号、日志和输入标识，再按下表处理。失败分类是恢复流程的权威来源；权限仍以仓库管理为准，正式发行草稿/Tag 的具体恢复仍按发布规范。

| 情形 | 可继续的范围与停止条件 |
| --- | --- |
| 同 SHA、同输入的临时网络/服务故障 | 本地入口仅对白名单只读命令自动重试最多 1 次，保留原失败和每次退出状态；额度按检查输入保留，重复 run 不能刷新。仍失败就停止该项并排查或等待外部状态变化，不循环重试 |
| 测试、语法、包或行为失败 | 在本任务已有授权范围内修复；变更后按测试规范只重跑受影响项，不关闭检查、不用旧包验收掩盖新变化 |
| 工具缺失、安装/系统配置变化或审批失败 | 报告实际缺项，继续不依赖它的工作；新增权限或环境改动按需询问，不以换工具通道绕过受限操作的审批 |
| 签名/凭据、证书、Tag 冲突、远端竞争或权限问题 | 不自动重试写入、改签名、移动 Tag、强推或降低门禁；保留证据，准备具体处理方案并取得所需授权 |
| 输入或来源 SHA 在执行中改变 | 当前结果失效，不按旧输入自动重试；重新核对范围、版本及材料，再执行受影响检查 |
| 用户暂停、操作取消或进程异常 | 不标通过；保存已完成项和剩余项。恢复时重新核对当前源码、配置、工具、远端基准及已有指示，按结果有效性继续，不只按阶段号跳转 |

本地 `run --pause-before 步骤` 会持久化 paused/剩余步骤；再次 run 复核输入后恢复，有效项复用。它不执行 Git 上传或 CI 跟踪，因此不会自行重跑远端发行。实际 GitHub 故障只能在已获准的跟踪/恢复范围内重跑原工作流与 SHA，不能把手动 Debug 修复入口扩大成手动正式发布。

源码、版本、目标或范围发生实质变化时更新最终审核单，重新取得受影响的测试结论与权限；旧任务/旧包许可不扩展到新内容。无需影响已明确且仍有效的决定。超出本任务的重构、破坏性迁移或新权限及时提问，不自行发散。

## 流程图同步维护

仓库 .agents/docs 中的[开发流程图](DEVELOPMENT_FLOWCHART.md)供用户审阅。每次修改阶段、判断条件、授权边界或回退路径，必须在同一次修改中同步更新流程图并检查图文一致。流程图不是临时文件，细则以本文件及各主题权威规范为准。

纯文档任务提供文档差异，不为人工审核额外构建 APK。按上述本地交付或最终审核路径处理；需要提交推送时仍须满足测试安排和权限两项条件，不能因是文档而自行免除。仅本地的代码任务依本地提交约定保存后交付并记录，纯文档无代码修改时不因此自动提交。

等待期间可在 ACCEPTANCE.md 记录“待人工测试/待答复”；该记录不授权提交。此阶段与发行前批准 master 合并是两项独立确认，也不替代后续 CI 产物验收。

## 最后一步：追加到 ACCEPTANCE.md

记录的权威时点：在最终材料与必要检查完成、提交前，先把已知事实写入 [ACCEPTANCE.md](ACCEPTANCE.md)；CI 尚未执行就写待执行。提交后的 SHA、CI/发布结果保存为工作区 temp 证据或真实 CI step summary，下次正常任务按需引用，不为追写本次 SHA/CI 自动制造新提交。第 9 阶段收尾核对交付与证据，不形成循环提交。

本地入口会从真实状态生成 `temp/<任务>/acceptance-draft.md`；`record --task 名称 --append` 显式追加，同一生成任务标记只追加一次，后续更新草稿与外部证据，不覆写原记录。人工维护也须先查看相关内容和末尾，保留历史，不另建同用途文件。每条使用“日期 + 任务名称”及下列三项：

- **内容**：一句话说明本次开发或更改了什么。
- **文件**：列出实际修改的文件；文件较多时按目录分组，并提供完整差异链接。
- **结果**：明确成功、部分完成或失败，简述实际检查结果；未完成或未验证的事项及原因用一句话说明。

有提交、CI 或可下载产物时，按需补充简短 SHA 和相关链接；没有则省略。不复述执行过程，不堆砌日志，不把推送成功、跳过检查或未运行测试写成全部验证成功。

用户要求仅修改本地文档时，记录也只保留在本地，不因此提交或推送。对话中简短告知记录已追加及实际结果即可。
