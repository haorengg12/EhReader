# 每次开发任务流程

本文件只维护阶段、默认版本意图及记录时点。先读[仓库入口](../../AGENTS.md)，按阶段读取主题规范，不批量预读全文。目录见[本地开发](LOCAL_DEVELOPMENT.md#工作区目录约定)，授权见[仓库管理](REPOSITORY_WORKFLOW.md)，版本算法与路径见[发布规范](RELEASE_POLICY.md)。2026-11-14 更新。

| 阶段 | 操作与按需阅读 | 完成证据 / 下一步 |
| --- | --- | --- |
| 1. 确认任务 | 核对分支、工作区、需求和当前版本 | 保留其他任务改动，明确范围及验证计划 |
| 2. 本地开发与版本准备 | 读本地开发规范；代码读编码规范，结构变化再读架构；版本/工作流改动读发布规范 | 普通维护不升版；测试包或上传目标不明先问版本；上传前三段必须合法提升，第四位仅本地 |
| 3. 自动检查与产物验证 | 按测试规范与本地矩阵检查；需要本地包时 Docker ARM64 Debug | 真实检查、输入、包与未测项；文档/流水线不额外编译 Android |
| 4. 最终审核 | 使用一份审核单，复用最终版本、测试安排和上传决定，仅问缺项 | 不要求上传时本地交付；第一位已确认版本且明确上传即覆盖后续助手自动合并 |
| 5. 本地提交与上传 | 读仓库管理；必要检查后代码任务在 develop 本地 commit；需要上传则固定 origin/develop 基准及上传计划 | 第一/二位推 develop，第三位推新的 develop-六位UUID，第四位仅本地；不自动提升版本 |
| 6. 按版本路径处理 | 第一/二位跟踪同 SHA 基础验证与 Debug；第三位只核对远端分支 SHA，第四位本地交付 | 第二位汇报 CI 后结束，第三位不运行任何远端 CI，均不创建 Tag/Release |
| 7. 第一位发行准备 | 复核固定 SHA、已确认版本与上传范围、develop 构建、PR 只读预检及实际保护 | 助手创建 develop → master PR，通过后以 Merge commit 自动合并，无需二次确认；失败/冲突/竞争停止 |
| 8. 正式发行 | 合并事件固定真实 merge SHA，正式构建、原证书签名、包及附件校验 | 自动创建正式 Tag、完整上传后公开 Release；继续跟踪并汇报实际结果 |
| 9. 核对记录与交付 | 核对提交前记录；提交后 SHA/CI 结果留 temp 或 CI summary | 不为追写本次结果制造循环提交，保留真实未测项 |

仅第一位进入第 7、8 阶段。普通本地任务仍按[本地提交约定](REPOSITORY_WORKFLOW.md#本地代码提交约定2026-11-10)保存，不自动推送。助手连续推进不能绕过未明确的版本、人工测试要求或上传许可；第一位合并的条件授权见仓库管理，不再额外索要一次合并批准。

## 节点推荐组合

以下是本项目的模型与推理等级建议。默认使用 **GPT-6.1 Sol + High**，减少阶段间切换；表中 Medium 是相应节点可选的节省资源配置，不要求每进入一个节点就切换。

| 开发流程节点 | 推荐模型 | 推理等级 | 使用说明 |
| --- | --- | --- | --- |
| 1. 确认任务 | GPT-6.1 Sol | High | 理解需求、范围、已有改动和验收条件；大型架构迁移可选 Astra + XHigh |
| 2. 本地开发与版本准备 | GPT-6.1 Sol | High | 常规实现、应用版本默认策略并完成所需修改；复杂并发、数据库迁移、核心架构调整可选 Astra + XHigh |
| 3. 自动检查与产物验证 | GPT-6.1 Sol | Medium | 执行检查、核对日志和产物；疑难失败先升 High，仍难定位再考虑 Astra + XHigh |
| 4. 最终审核 | GPT-6.1 Sol | Medium | 针对最终材料用同一审核单处理测试安排与保存权限，只补齐缺项 |
| 5. 本地提交与上传 | GPT-6.1 Sol | Medium | 核对差异、暂存区、授权和目标分支，执行提交推送 |
| 6. 按版本路径处理 | GPT-6.1 Sol | Medium | 第一、二位跟踪 CI；第三位只保存临时分支，第四位本地交付；需要修复时按第 2 节点重新选择 |
| 7. 发行准备与确认 | GPT-6.1 Sol | High | 第一位核对已确认版本、上传授权、固定提交、CI 及合并条件 |
| 8. 正式发行 | GPT-6.1 Sol | Medium | 执行已批准操作，核对签名、Tag、Release 和附件；异常涉及发布逻辑时升 High |
| 9. 核对记录与交付 | GPT-6.1 Sol | Medium | 根据实际证据核对任务记录与收尾材料 |

- 表中 Astra 指 GPT-6 Astra。Max、Ultra 不绑定固定节点：第 1、2 节点需要深入推理的单个难题可考虑 Max；第 1、2、3 节点涉及可独立拆分的大型分析或审查时可考虑 Ultra。
- 需要升级时简短说明当前节点、具体难点及推荐组合，由用户决定是否切换；建议本身不新增等待条件，用户明确要求等待切换时暂停相关工作。
- 无法可靠确认当前模型或推理等级时不推测，不声称已完成切换；实际选项以客户端为准。模型选择不改变各阶段的验证、授权及发布条件。
- 本表为项目使用建议，参考 [OpenAI 模型与推理等级说明](https://learn.chatgpt.com/docs/models)，不是官方固定配置或自动切换机制。

## 临时文件存放

所有阶段主动生成或导出的临时日志、排查记录、调试输出、临时报告和一次性辅助文件，统一存放在工作区根目录 `D:\Eh项目改造\temp`，不是 `EhReader/temp`。需要时创建目录，建议按 `temp/<日期-任务>/<阶段>/` 分组，避免文件混杂或覆盖其他任务记录；不将这些临时文件提交到仓库。

工具固定生成的容器中间文件和缓存按既有构建机制管理，需要导出用于排查时放入上述 temp 目录。用于本地构建的替换文件仍放在工作区 `build-tools/build-use-file`；本地 arm64-v8a APK 及配套校验清单、来源清单和最终验收报告放在工作区 `release`；最终简短结论追加到仓库[ACCEPTANCE.md](ACCEPTANCE.md)，必要时链接 temp 中的详细排查记录。废弃文件或目录回收到工作区 `trash`，不混入有效交付材料；目录管理遵循[工作区目录约定](LOCAL_DEVELOPMENT.md#工作区目录约定)。

本规则适用于后续文件存放，不自动迁移或删除既有记录。仅更新规范不代表现有构建脚本的日志输出路径已经适配。

## 版本准备（第 2 阶段）

普通功能、修复、文档、配置和必要编译默认保留版本；不要因为执行检查而自行升版。已明确版本直接沿用，不重复问。交付测试包但版本未明确时，先确认沿用还是升版；需要上传而目标三段版本不明确时，只暂停依赖该决定的最终版本准备和上传，可继续无关本地工作。

第四位仅本地 Debug，三段省略的第四位视为 0；多位变化只取最左侧变化位。上传前必须确认并修改为合法递增三段版本，versionCode 独立递增，不能仅去掉第四位形成降版。具体数字算法和远端比较基准统一见发布规范；本地源码修改不能用 CI 或推送后临时改文件代替。

第 3 阶段可用[本地任务调度入口](LOCAL_DEVELOPMENT.md#本地任务调度入口)执行已支持的检查及材料整理；该入口不执行上传、CI 跟踪或合并，也不自行取得权限。继续任务按[检查复用规则](TESTING_STANDARDS.md#检查结果的复用与失效)核对输入，不把旧包当作新包验收。

## 人工测试安排确认

### 最终审核单

- **改动**：本次范围、结果和必要风险。
- **范围**：拟提交文件、最终差异和已有 SHA；不夹带其他任务文件。
- **版本与目标**：不升版或具体 versionName/versionCode；需要上传时列固定 origin/develop 基准、目标分支和唯一路径。
- **验证**：本地真实结果、未测项，以及人工测试待安排/待结果/通过/未通过/无需等待。
- **材料**：最终包或差异、输入来源和证据；纯文档不为审核额外打包。
- **处置**：仅本地，或明确上传本次内容；第一位列明后续助手跟踪 CI、创建 PR、Merge commit 自动合并及正式发行，第二位到 CI 汇报结束，第三位到快照保存结束。

用户测试通过不自动授权推送，允许推送也不取消明确要求等待的测试。复用已有充分指示，只问缺少的决定。不上传的代码任务完成必要检查后按持续授权本地 commit，未要求设备测试时不为保存代码等待设备验收。纯文档没有代码修改时不因此自动提交。

### 推送授权

只有版本、内容、目标及测试条件已明确且上传已获准才推送。第一位上传条件满足时，用户已授权助手在构建和 PR 门禁通过后连续合并及发布，不再要求具体 PR 二次确认。第二位许可不扩展为 master 合并；第三位许可仅覆盖新 UUID 快照分支；第四位不能上传。

### 关键人工审核节点

1. 目标、版本或范围不明时及时提问，只暂停依赖该答复的操作。
2. 本次结果与上传采用同一审核单一次补齐缺项，复用已有授权，不因 CI 成功补造许可。
3. 第一位发行准备核对固定输入、权限和实际门禁，不增加二次合并问答；实质变更、新提交或远端竞争时重新核验受影响结果和范围。

## 第 5～8 阶段连续推进

上传前 fetch 并固定最新 origin/develop SHA，生成只读上传计划，核对全部本地待上传提交；推送后验证目标完整 SHA。第一/二位跟踪同 SHA 的基础验证与 Debug 构建；第二位汇报结果后结束。第三位快照不运行 CI，核对分支 SHA 后结束。第四位仅本地交付。

第一位 CI 成功后助手创建同仓库 develop → master PR，复核 Release readiness 和全部实际必需检查，使用 expected head SHA 以 Merge commit 合并；随后连续跟踪 merge SHA 正式构建和 Release，不能把合并成功当作发行成功。助手在当前任务持续跟踪，不新增后台机器人、长期令牌或手动发布入口。

## 失败恢复与重新审核

先保存实际命令、退出码/取消信号、日志和输入标识，再按下表处理。失败分类是恢复流程的权威来源；权限仍以仓库管理为准，正式发行草稿/Tag 的具体恢复仍按发布规范。

| 情形 | 可继续的范围与停止条件 |
| --- | --- |
| 同 SHA、同输入的临时网络/服务故障 | 本地入口仅对白名单只读命令自动重试最多 1 次，保留原失败和每次退出状态；额度按检查输入保留，重复 run 不能刷新。仍失败就停止该项并排查或等待外部状态变化，不循环重试 |
| 测试、语法、包或行为失败 | 在本任务已有授权范围内修复；变更后按测试规范只重跑受影响项，不关闭检查、不用旧包验收掩盖新变化 |
| 工具缺失、安装/系统配置变化或审批失败 | 报告实际缺项，继续不依赖它的工作；新增权限或环境改动按需询问，不以换工具通道绕过受限操作的审批 |
| 签名/凭据、证书、Tag 冲突、远端竞争或权限问题 | 不自动重试写入、改签名、移动 Tag、强推或降低门禁；保留证据，准备具体处理方案并取得所需授权 |
| 输入或来源 SHA 在执行中改变 | 当前结果失效，不按旧输入自动重试；重新核对范围、版本及材料，再执行受影响检查 |
| 用户暂停、操作取消或进程异常 | 不标通过；保存已完成项和剩余项。恢复时重新核对当前源码、配置、工具、远端基准及已有指示，按结果有效性继续，不只按阶段号跳转 |

本地 `run --pause-before 步骤` 会持久化 paused/剩余步骤；再次 run 复核输入后恢复，有效项复用。它不执行 Git 上传或 CI 跟踪，因此不会自行重跑远端发行。实际 GitHub 故障只能在已获准的跟踪/恢复范围内重跑原工作流与 SHA，不能把手动 Debug 修复入口扩大成手动正式发布。

源码、版本、目标或范围发生实质变化时更新最终审核单，重新取得受影响的测试结论与权限；旧任务/旧包许可不扩展到新内容。无需影响已明确且仍有效的决定。超出本任务的重构、破坏性迁移或新权限及时提问，不自行发散。

## 流程图同步维护

修改阶段、条件、权限或恢复路径时，必须同步[开发流程图](DEVELOPMENT_FLOWCHART.md)，人工审阅图文一致；链接检查不证明流程语义正确。规范主题各自保持唯一权威来源，历史记录按当时事实保留。

## 最后一步：追加到 ACCEPTANCE.md

记录的权威时点：在最终材料与必要检查完成、提交前，先把已知事实写入 [ACCEPTANCE.md](ACCEPTANCE.md)；CI 尚未执行就写待执行。提交后的 SHA、CI/发布结果保存为工作区 temp 证据或真实 CI step summary，下次正常任务按需引用，不为追写本次 SHA/CI 自动制造新提交。第 9 阶段收尾核对交付与证据，不形成循环提交。

本地入口会从真实状态生成 `temp/<任务>/acceptance-draft.md`；`record --task 名称 --append` 显式追加，同一生成任务标记只追加一次，后续更新草稿与外部证据，不覆写原记录。人工维护也须先查看相关内容和末尾，保留历史，不另建同用途文件。每条使用“日期 + 任务名称”及下列三项：

- **内容**：一句话说明本次开发或更改了什么。
- **文件**：列出实际修改的文件；文件较多时按目录分组，并提供完整差异链接。
- **结果**：明确成功、部分完成或失败，简述实际检查结果；未完成或未验证的事项及原因用一句话说明。

有提交、CI 或可下载产物时，按需补充简短 SHA 和相关链接；没有则省略。不复述执行过程，不堆砌日志，不把推送成功、跳过检查或未运行测试写成全部验证成功。

用户要求仅修改本地文档时，记录也只保留在本地，不因此提交或推送。对话中简短告知记录已追加及实际结果即可。
