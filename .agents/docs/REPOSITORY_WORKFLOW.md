# 仓库管理规范 — V3.0

本文件是分支、授权、提交、上传和助手自动合并的权威来源；算法与路径见[发布规范](RELEASE_POLICY.md)，阶段见[开发流程](DEVELOPMENT_FLOW.md)。

## 本地代码提交约定（2026-11-10）

用户持续授权每次代码修改完成且必要检查通过后，在 develop 做一次本地 commit，不创建 Tag、不自动推送、不自动升版。只提交本任务文件，保留其他改动；本地保存不等待未要求的设备验收，未测项如实记录。纯文档无代码修改时不因此自动提交。此授权与 2026-11-14 新上传分流互补：普通本地任务仍不自动上传。

## 状态与授权范围

2026-11-14 用户明确确认四位版本路径，并对第一位路径授予条件授权：确认最终版本且明确要求上传本次内容后，推送 develop，跟踪同 SHA 的基础验证及 Debug 构建；全部成功后由助手创建 develop → master PR，等待实际必需检查和 Release readiness，通过后以 Merge commit 合并，无需二次确认具体 PR；随后连续验收正式发行。该新授权取代“master 合并始终另行确认”的旧要求，仅覆盖该第一位上传任务，不覆盖无关内容。

第二位只推送 develop、构建并汇报；第三位只推送新的 develop-六位UUID 分支，此操作纳入已确认的第三位上传任务授权，不运行远端 CI、不创建 PR、不合并；第四位仅本地。普通保存三段版本可在明确上传授权后推送 develop，仅基础检查。算法、基准、第四位归零及安装编号见发布规范，不另复制。

版本确认不自动等于要求上传，CI 成功也不自动取得普通上传许可。人工测试通过、明确无需等待、允许上传三者含义分别记录；复用已有充分答复，不重复提问。实质变化时重新核验受影响的材料与权限，不能沿用旧包验收或把授权扩大到其他任务。

助手自动合并前提供或保留可审阅的完整 SHA、差异、最终版本、测试实际结果和 CI 链接；确认实际保护、签名与版本门禁已满足。使用固定 expected head SHA 合并；出现新提交、保护缺失、失败、冲突或远端竞争时停止合并并报告。不可用管理员绕过、关闭检查、强推或移动标签解决。第二位即使 CI 通过也不得自动创建 PR 或合并。

GitHub 内不新增自动合并机器人或长期令牌。助手仅在本次任务中持续跟踪，不承诺任务结束后仍有后台监控；中断后恢复时重新核对同一输入与授权，不能只凭旧状态合并。

## 分支与任务交付

- master 为默认分支，接收第一位发行 PR 的 Merge commit，不日常直接开发。
- develop 为本地开发、第一/二位上传及普通三段保存分支；上传前 fetch，固定最新 origin/develop 基准，检查祖先关系和完整差异。
- develop-六位UUID 为第三位快照分支，六位后缀取 UUID 十六进制字符；仅保存，不运行 CI。先检查远端不存在同名分支，冲突重新生成，不复用覆盖。后续不自动删除或合并。
- 第四位仅在本地 develop 提交和 Debug 测试；历史远端四段提交及 brody 分支保留，不自动清理。新上传必须准备递增三段版本。
- 每次推送前核对最终审核单、暂存范围和已确认条件。可以使用只读 upload-plan 入口留存计划，具体算法见[发布规范](RELEASE_POLICY.md#比较基准与合法性)。远端基准改变后重新比较，不强推。
- 删除远端分支、Tag、改写历史、修改仓库设置或写入旧 EhViewer 不属于普通任务授权；已有针对本任务的明确指示优先。源码、密钥、产物、缓存和凭据的保存边界维持现有规定。

## CI 与用户确认

1. 第一/二位上传后核对远端完整 SHA，按事件、工作流和 SHA 跟踪 Basic quality 与 Development Debug，提供检查、附件及失败原因，不能只报告推送成功。
2. 第一位成功后由助手连续完成获准 PR、必需检查、Merge commit 和正式发行验收；PR 检查不重复构建 Debug。第二位在汇报 CI 后结束。
3. 第三位仅核对远端快照分支 SHA 并汇报，不等待不存在的流水线。第四位只交付本地结果。
4. 失败、取消、NO-SOURCE、未执行分别记录，不静默重试写入、不关闭门禁。同 SHA 临时故障和实质修复按开发流程及发布规范恢复。
5. 正式发行固定真实 merge SHA 重新构建并使用原证书签名，核对 Tag、Release 与全部附件。只有同仓库 develop → master 的已合并 PR 事件可触发，不手动造 Tag 触发发布。
6. 实际远端门禁部署前另行核实：目标必需检查 Basic quality、Release readiness，严格同步且管理员生效。不要把规范当成已经生效的设置；迁移状态见[发布规范](RELEASE_POLICY.md#尚待实现的适配)。

## 技术启用状态

本次仅本地适配并按持续授权提交，不推送、不配置新凭据、不触发发行。正式工作流获准按版本路径部署到 master 后才生效；现有公开 Tag 和 Release 保持原状。远端实测与本地单元测试分别记录。
